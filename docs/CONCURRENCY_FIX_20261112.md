# 并发缺陷定位与修复报告（2026-11-12）

本轮从「浏览器交互级深测」出发，抓到一个真实的并发缺陷并修掉，同时用数据否掉了一条看起来更优的方案（WAL）。
所有数字都是本机实测，脚本可复跑。

---

## 1. 一句话结论

**每个 HTTP 请求都要写两次数据库**（`session` 心跳 + `access_log`），把只读请求也变成了写请求；
在回滚日志模式下写事务与读事务互斥，多人同时刷新就会互相锁死，表现为 503 `DB_BUSY` 与 5–8 秒的卡顿。
把这两处写改成「按需 / 攒批」后，课堂节奏下**失败率 0%、p50 从 42ms 降到 20ms、p95 从 7.2 秒降到 0.15 秒**。

---

## 2. 问题是怎么被发现的

1. 浏览器深测（`test-tmp/cdp/deep-ui-20261112.js`）在收尾的网络检查里报出两条 503：
   `/api/v1/courses?page=1&page_size=100`、`/api/v1/courses/16/knowledge-graph`。
2. 单独复跑这两个端点，10/10、3/3 全 200 —— 说明不是稳定故障，只在并发下出现。
3. 后端把 `sqlite3.OperationalError` 映射为 `503 DB_BUSY`（`backend/app.py:156-162`），
   而 `backend/shared/db.py:19` 已经设了 `busy_timeout=5000`。等了 5 秒还拿不到锁，说明不是「短暂争用」。
4. 写探测脚本 `scripts/db_busy_probe_20261112.py`：**6 读 + 2 写跑 12 秒，5.52% 请求 503，p95 7.5 秒、最慢 8.7 秒**。

> 脚本的写侧用的是 `PUT /courses/16/me/seat` 传本人当前座位：命中
> `seat_swap.py:200` 的「位置没变」分支直接返回，只取写锁、不写行、不落审计，测完库是干净的。

---

## 3. 根因

`sqlite3` 的 `isolation_level=None` 让每条语句自动提交，于是每个请求至少产生两个写事务：

| 位置 | 行为 | 说明 |
| --- | --- | --- |
| `backend/shared/auth.py:35` | 每个已登录请求 `UPDATE session SET last_seen_at, expires_at` | 会话是 2 小时滑动过期，但续期写成了「每请求一次」 |
| `backend/apis/logs.py:37` | 每个请求 `INSERT INTO access_log` + `commit` | 一次访问 = 一次 fsync |

回滚日志（`journal_mode=delete`）下，写事务提交要拿 EXCLUSIVE 锁，读者持 SHARED 会挡住它；
一旦形成「读者不断、写者拿不到锁」的排队，写者的 PENDING 状态又挡住后来的读者，
整条链路一起堆在 `busy_timeout` 上，最后一起超时返回 503。

实测证据：**零写入、12 个纯读线程**仍然 8.8% 请求 503、p95 7.4 秒 ——
因为「纯读」其实也不纯：攒批的那一次落库就在读线程里发生。

---

## 4. 被否掉的方案：WAL

WAL 是这类问题的标准解。实测结果相反 —— **这台机器上多连接 WAL 不可用**：

| 场景 | 结果 |
| --- | --- |
| WAL，1 个连接（1 读 0 写，5 秒） | 532,500 次操作，**0 失败** |
| WAL，2 个连接（2 读 1 写，5 秒） | **74.79% 失败**，全部 `SQLITE_READONLY: attempt to write a readonly database` |
| WAL，8 个连接（6 读 2 写） | **90.27% 失败** |
| 同上，换 PowerShell 通道复跑 | **90.31% 失败**（排除 bash 沙箱因素） |
| 换到 C:\Temp 目录 | 83.01% 失败（排除 D: 盘因素） |
| D: 是 NTFS 固定盘 | 已确认，不是文件系统不支持 |

WAL 下 `-wal` 文件始终 0 字节，写入根本没进 WAL 索引。结论：**不是并发放大，是 WAL 在本机直接不成立**，
`journal_mode` 已还原为 `delete`，库完整性 `PRAGMA integrity_check = ok`、`foreign_key_check` 无违规。

> HTTP 层用 WAL 跑过一次：906 请求 / 12 秒、0 个 `DB_BUSY`、p95 278ms（相对 delete 模式的 145 请求 / 12 秒、p95 7494ms），
> 确实好得多，但会换来 0.3% 的 `SQLITE_READONLY` 500。在问题定性清楚之前不能把这种模式交出去，故放弃。

## 5. 最终改动

### 5.1 `backend/shared/auth.py` —— 会话心跳限频

- 新增 `HEARTBEAT_SECONDS = 60` 与 `_heartbeat_due()`：距上次续期不足 60 秒就不再写库。
- 续期写失败（`sqlite3.OperationalError`）只记一条 warning，不再把本次请求打成 500/503。
  续期只是「最近活跃」的记账，不该反压业务。
- 会话有效期 2 小时，60 秒续一次足够保证活跃会话不超时。

### 5.2 `backend/apis/logs.py` —— 访问日志攒批落库

- 请求结束后只把记录追加到内存列表，**够 20 条或距上次落库超过 2 秒**才一次性 `executemany + commit`。
  写库次数降到约 1/20，且不再让每个读请求都 fsync。
- `_filtered()`（日志导出的公共入口）先 `flush_access(force=True)`，
  保证教师导出的 CSV/JSON 一定包含刚刚发生的访问。
- `atexit` 兜底：正常退出时用独立连接补写尾部记录；进程被强杀最多丢 2 秒日志。
- 落库失败只记 debug 并回滚，绝不影响业务响应（原注释里就是这个约束）。

### 5.3 `frontend/index.html` —— 内联 SVG favicon

浏览器每个页面都请求 `/favicon.ico` 得到 404，控制台常驻一条红字。补一个内联 data-URI 图标，不新增文件。
实测 `favicon.ico 404` 从每页 1 次降到 0 次。

## 6. 前后对照（同一负载、同一份干净库）

负载：20 个读线程各隔 1 秒刷新 + 2 个写线程各隔 1 秒签到，跑 20 秒（约 22 请求/秒，接近一个班上课的节奏）。

| 版本 | 请求数 | 失败 | p50 | p95 | 最慢 |
| --- | --- | --- | --- | --- | --- |
| 原版 第 1 轮 | 438 | 0 | 42.4ms | 111.0ms | 223.9ms |
| 原版 第 2 轮 | 285 | 8（2.81%） | 43.7ms | **7198.2ms** | 8183.9ms |
| 修复版 第 1 轮 | 440 | **0** | 23.5ms | 155.7ms | 200.4ms |
| 修复版 第 2 轮 | 440 | **0** | 20.3ms | 163.3ms | 288.0ms |
| 修复版·演示实例 5000 | 440 | **0** | 20.7ms | 149.5ms | 214.5ms |

满载（6 读 + 2 写，不间歇）下：失败率 5.52% → 1.75%，p50 171ms → 71ms，吞吐 145 → 456 请求。
**满载 12 个不间断读线程时仍会出现 5–7 秒排队**（约 6%），这是回滚日志模式「读者之间被写者串起来」的固有代价，
在 WAL 不可用的前提下无法根除；但这个强度已经是 48 请求/秒的持续压力，远超课堂实际。

## 8. 遗留风险（未修，需产品决策）

1. **`access_log` 无上限**：今天一天的测试就积到 2.1 万行。长期跑会越来越慢，
   建议加保留策略（如只保留 90 天）或定期归档，属于功能取舍不是缺陷。
2. **`session` 无过期清理**：`session` 表现有 739 行，多数已过期。建议登录时顺手删掉过期会话。
3. **满载排队**：见第 6 节，回滚日志模式的固有代价。若后续换到 WAL 可用的部署环境，
   在 `db.py:connect()` 里加 `PRAGMA journal_mode=WAL` 即可；**但换环境前必须用第 4 节的脚本复验**，
   否则可能重演本机 90% 失败的情况。
4. **开发服务器**：目前跑的是 Werkzeug 开发服务器（`app.py:234`），并发能力有限。
   答辩演示够用，若要真实承载多人同时签到，建议换 waitress/gunicorn。
